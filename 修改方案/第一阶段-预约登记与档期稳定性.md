# 第一阶段：预约登记与档期稳定性

## 1. 阶段定位

当前应用是小体量的摄影师/妆娘排单工具。模特在提交公开预约前，已经通过微信、电话或线下与服务者沟通好了拍摄时间，因此本阶段不建设服务者审核环节。

本阶段的业务流程是：

```text
提前沟通确认 -> 公开页面登记预约 -> 自动进入服务者排单 -> 返回订单回执 -> 拍摄提醒 -> 服务者完成订单
```

目标是让预约登记足够可靠，同时减少重复沟通和档期录入错误。

## 2. 明确不做的设计

- 不新增独立模特端。
- 不增加“待服务者确认”状态。
- 不增加服务者审核中心。
- 不增加预约占位 15 分钟和自动过期释放。
- 不要求公开预约用户提交后等待服务者确认。
- 不在公开页面直接修改服务者档期。

公开预约仍然是一个页面，预约提交成功后直接生成正常排单。现有 `normal` 状态继续代表已登记、可执行的排单。

## 3. 现有页面如何承载结果

### `/model-booking`：预约提交页

提交成功后，当前页面先显示结果摘要：

- 预约登记成功；
- 服务者名称；
- 拍摄日期和时间；
- 拍摄地点；
- 订单编号；
- 当前状态：已登记；
- 复制订单链接按钮；
- 查看订单详情按钮。

当前页面可以在短暂展示成功反馈后，继续跳转到现有 `/order/:bookingGroupId`，不新增独立结果页。

### `/order-query`：公开订单查询页

查询结果增加状态标签：

```text
已登记 / 部分完成 / 已完成 / 已取消
```

点击结果后进入现有订单详情页。

### `/order/:bookingGroupId`：公开订单详情页

作为预约提交后的长期回执页面，展示：

- 订单整体状态；
- 每个服务项目的服务者、时间和状态；
- 拍摄地点和需求说明；
- 参考图；
- 订单编号和创建时间；
- 联系服务者入口；
- 复制订单链接；
- 必要时的取消说明。

订单详情可以展示“已登记”，但不要展示“待确认”。

### 服务者端

服务者继续使用现有 `/home`、`/calendar` 和 `/schedule/:id`：

- 首页直接显示刚登记的排单；
- 日历显示排单日期；
- 详情页继续编辑时间、地点、备注、收款和参考图；
- 不新增待确认预约列表。

## 4. 预约提交流程

### 提交前复核

提交按钮前增加订单摘要区域，要求公开预约用户确认：

```text
我已与服务者沟通并确认以上时间、地点和服务内容
```

复核内容包括：

- 服务者；
- 服务角色；
- 日期和时间；
- 拍摄地点；
- 客户姓名和手机号；
- 服务需求；
- 参考图片。

这个勾选只是防止误提交，不产生服务者审核状态。

### 提交成功

后端继续创建正常排单，返回：

- `bookingGroupId`；
- 订单状态；
- 安全订单 Token；
- 服务项目列表；
- 订单详情链接。

成功提示文案建议为：

```text
预约登记成功，已加入服务者排单。
如需修改时间，请直接联系服务者。
```

## 5. 档期和冲突规则

### 公开可预约规则

服务者设置中增加：

- 每周工作日；
- 每日工作时间；
- 午休时间；
- 最短提前预约时间；
- 拍摄前准备时间；
- 外景移动缓冲时间；
- 不可预约日期。

例如：

```text
工作时间：09:00 - 21:00
最短提前预约：4 小时
订单间隔缓冲：30 分钟
周一休息
```

### 冲突判断

- 公开预约只与 `normal` 状态的排单判断冲突；
- `stored` 暂存订单不应占用公开可预约档期；
- `completed` 已完成订单不应影响未来预约；
- 提交时必须由后端再次校验，不能只依赖前端可用时间展示；
- 同时提交时需要使用事务或数据库锁，避免重复预约同一时间。

服务者手动录入排单可以超出公开预约规则，但提交时应提示“当前时间不在公开可预约规则内”。

## 6. 修改、取消和完成

### 修改

由于预约前已经沟通完成，改期不做公开端自动改期流程：

1. 模特联系摄影师或妆娘沟通变更。
2. 服务者在 `/schedule/:id` 中修改日期和时间。
3. 后端重新校验冲突。
4. 订单详情刷新后展示最新时间。

### 取消

第一阶段可以由服务者在排单详情中取消或删除预约。公开订单详情只展示“如需取消请联系服务者”，不直接让公开用户删除排单，避免误操作。

### 完成

继续使用现有“完成订单”能力。公开订单状态根据关联服务项目计算：

- 全部正常：已登记；
- 部分完成：部分完成；
- 全部完成：已完成。

## 7. 轻量提醒

小体量场景不需要先建设复杂消息中心和短信系统，第一阶段只做轻量提醒：

- 服务者首页显示今日和明日排单；
- 排单卡片显示即将开始和进行中状态；
- 沿用现有拍摄前一天、拍摄前一小时提醒配置；
- 公开订单详情提供“添加到手机日历”入口，条件允许时调用系统日历能力；
- 不接入短信、微信模板消息和独立通知服务。

如果后续订单量增加，再单独建设通知中心。

## 8. 数据调整建议

### `booking_groups`

不新增待确认状态，建议增加或明确：

- `status`：`registered`、`partially_completed`、`completed`、`cancelled`；
- `source`：`public` 或 `manual`；
- `shareToken`：公开订单安全访问 Token；
- `cancelledAt`；
- `cancelReason`。

### `schedules`

继续使用现有状态：

```text
normal / stored / completed
```

如需要区分取消，建议增加 `cancelled`，不要使用“待确认”代替取消。

### `user_settings`

增加一个结构化的 `availabilityRules` 配置，第一阶段可以先使用 JSON，后续用户量增加后再拆成独立表：

- 工作日；
- 开始和结束时间；
- 休息时间；
- 提前预约小时数；
- 缓冲分钟数；
- 不可预约日期。

## 9. 接口调整建议

保留现有公开预约接口：

```text
POST /public/bookings
GET  /public/availability
GET  /public/orders
```

接口调整：

- `POST /public/bookings` 继续直接创建正常排单；
- 返回 `status: registered` 和安全 Token；
- `GET /public/orders` 返回订单整体状态和每个服务项目状态；
- `GET /public/orders/:token` 根据安全 Token 返回公开订单详情；
- `GET/PATCH /settings` 支持公开可预约时间规则；
- 现有 `PATCH /schedules/:id` 继续负责服务者修改排单；
- 现有删除接口需要明确展示为取消或删除，避免公开订单出现状态丢失。

本阶段不新增以下接口：

```text
/booking-requests
/booking-requests/:id/confirm
/booking-requests/:id/reject
/booking-requests/:id/propose-time
```

## 10. 权限和隐私

- 订单详情不能只凭连续可猜测的订单编号访问；
- 建议使用订单 Token，或订单编号加手机号校验；
- 公开订单尽量隐藏完整手机号；
- 公开链接只允许查看该订单，不能访问服务者其他客户；
- 邀请码管理只允许管理员使用；
- 服务者编辑排单时必须校验订单归属。

## 11. 验收标准

1. 公开预约提交后立即生成正常排单。
2. 不出现待确认、服务者审核和等待确认页面。
3. `/model-booking` 能展示提交成功摘要并跳转订单详情。
4. `/order-query` 能展示订单状态标签。
5. `/order/:bookingGroupId` 能展示订单整体状态和服务项目状态。
6. 公开预约提交时能校验工作时间、休息日和档期冲突。
7. 暂存订单不错误占用公开可预约档期。
8. 服务者可以从现有排单详情修改日期、时间和地点。
9. 修改后公开订单详情展示最新数据。
10. 订单详情访问具备 Token 或手机号校验。

## 12. 实施顺序

1. 调整公开预约成功返回值和订单状态字段。
2. 改造 `/model-booking` 提交成功展示。
3. 改造 `/order-query` 和 `/order/:bookingGroupId` 状态展示。
4. 增加安全订单 Token 和公开信息脱敏。
5. 增加工作时间、休息日、提前预约和缓冲规则。
6. 修正公开档期和后端冲突判断。
7. 补充服务者端修改、完成和轻量提醒的验收测试。

## 13. 本阶段暂不实施

- 服务者确认预约；
- 待处理预约中心；
- 公开端自动改期；
- 在线支付和退款；
- 服务套餐和复杂报价；
- 客户画像和复购营销；
- 后期交付管理；
- AI 自动生成拍摄方案；
- 短信、微信模板消息和复杂通知中心。
