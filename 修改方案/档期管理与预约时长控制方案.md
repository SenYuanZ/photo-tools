# 档期管理与预约时长控制方案

日期：2026-10-09
状态：代码分析及方案，尚未实施。

## 1. 核心结论

公众预约改成「选择服务时长 + 选择可约开始时间」，由后端计算结束时间。服务者管理「开放时间、服务时长、缓冲时间、特殊日期、临时封档」。可用档期以服务者本人为资源统一计算，公开展示与提交、管理端新增、编辑、恢复使用同一规则。

保持当前直接登记流程，不引入审批队列或浏览页面即占位。

## 2. 已核实的问题

- server/src/public-booking/public-booking.service.ts 默认生成全天 00:00–24:00 的 30 分钟网格，未体现营业时间。
- 空闲网格通过 buildRanges 合并成连续 freeRanges，空白的一天会形成一个很长的空闲区间。
- app/src/views/modelBooking/components/BookingServiceCard.vue 将 freeRanges 做成可点击预约选项。
- app/src/views/modelBooking/hooks/useModelBooking.ts 的 applyFreeRange 同时填入区间的开始和结束，把空闲区间长度变成预约时长。
- 公众预约和排单创建缺少公众时长上限、营业窗口和提前预约限制；现有时间工具主要验证结束晚于开始及区间相交。
- 24:00 会出现在空闲区间尾端，但公众 DTO 时间正则只接受 00:00–23:59。因此整段点击有时会先被其他校验阻止，不能声称每次都成功提交整天；客户仍可手动选择并提交很长的合法时间段。
- 公开档期可按服务类型过滤，而公共登记预检按服务者全部类型查询，可能出现展示可约但提交冲突。
- 公开档期与公共登记预检只过滤 displayStatus=Y，排单冲突检查只过滤 normal，状态占用口径不一致。
- blockedSet 从排单实际开始分钟按 30 分钟递增。09:10–10:10 等非网格时间不能可靠匹配全天半小时网格，应改用区间相交判断。
- 当前公共登记先检查后依次保存预约组、客户和排单，未见覆盖完整流程的事务与档期资源锁，存在并发重复和部分登记风险。部分管理端操作虽然有保存事务，但冲突检查不在统一资源锁内。

## 3. 推荐的首期规则

以下数值是建议初始值，供服务者配置，尚未由业务确认。

| 项目 | 建议初始值 | 规则 |
| --- | --- | --- |
| 周开放时间 | 09:00–12:00、13:00–18:00 | 可按星期分别设置；明确关闭的日期不开放 |
| 公众服务时长 | 60、90、120 分钟 | 服务者可按服务类型启用选项，默认 90 分钟 |
| 公众单次上限 | 120 分钟 | 较长业务由服务者自行登记，后续可显式启用半天/全天服务 |
| 开始时间步长 | 30 分钟 | 决定开始时间候选，不代表服务时长 |
| 准备/收尾缓冲 | 前置 0、后置 30 分钟 | 计入资源占用，提交时保存快照 |
| 最短提前预约 | 2 小时 | 使用北京时间及服务端当前时间计算 |
| 最远开放日期 | 未来 30 天 | 随日期自动滚动 |
| 是否跨日 | 首期不支持 | 避免现有单 date + 起止时间合同歧义 |

公众预约一次只能选择服务者开放的时长。即使某天完全空闲，也只能预约本次选定时长。

准备和收尾使用同一套区间扩展规则：占用开始 = 服务开始 - 前置缓冲，占用结束 = 服务结束 + 后置缓冲。相邻两单需要预留前一单收尾与后一单准备之和；首期前置为 0，避免无意叠加双份间隔。

首期要求扩展后的占用完整落在同一个开放窗口内，不能跨午休、休息日或闭店边界。若需要收尾延长到闭店后，未来应明确新增规则，不隐式放行。

## 4. 服务者的档期管理

### 4.1 周规则

在「我的 → 档期管理」设置：

- 是否开放公众预约。
- 每个星期的开放窗口，可有多个时间段。
- 不同服务类型的时长选项、默认时长和公众上限。
- 前后缓冲、预约提前量和开放天数。

同一个人的摄影、妆造等角色共享资源占用，只在时长、服务资格等规则上区分。

### 4.2 特殊日期

指定日期可以关闭全天，或替换为特殊开放窗口。特殊日期覆盖周规则，显式空窗口代表当天关闭，缺少特殊日期配置才继承周规则。

服务者可在日历中封锁半天、几个小时或整天，记录休假、出差、交通等原因。公开页面只显示不可约，不返回私人备注。

临时封档与已有排单冲突时，默认禁止保存，并列出受影响排单供服务者改期；禁止静默取消已有预约。

### 4.3 日历展示与手工登记

日历区分：开放空闲、预约服务、前后缓冲、休息/封档。展示当日安排和最长连续可约时长，不将可选开始时间数量等同于还能接多少单。

手工登记允许自定义服务时长、夜间或全天业务；超出公众开放规则需要服务者明确确认并记录覆盖理由。身份权限由后端验证，不能依靠前端开关。

手工登记仍不得重叠其他预约或封档；先改期或解除封档后再安排。首期每名服务者同一时间容量为 1，不提供重叠强制登记。

## 5. 客户预约页面

1. 从普通入口或专属二维码进入，选定服务者及本次角色。
2. 选择该服务者提供的服务时长。
3. 日期只标识对该时长确实存在可约开始时间的日期。
4. 显示可约开始时间，如 09:00、09:30、10:00，而不是可整段预约的 09:00–18:00。
5. 选择开始时间后自动展示「09:30–11:00 · 90 分钟」，客户不再自由设置结束时间。
6. 提交成功直接登记并展示预约结果。

切换服务者、角色、日期或时长后重新请求档期；旧选择无效时清空并提示，不静默改到另一个时间。加载、错误、无可约时间时禁用时间选择和提交；不能把接口错误解释成全天可约。

连续空闲区间可以作为辅助概览，但不再点击后填入完整区间。空状态区分未开放、时长放不下、已约满、提前量不足和加载失败，并建议缩短时长或更换日期。

## 6. 档期计算方法

可约开始时间是同时满足以下条件的候选：

- 服务者有效、支持所选角色和服务时长。
- 日期在预约开放范围内，开始时间满足提前量。
- 服务时长由后端配置解析，结束时间由后端计算。
- 扩展后的占用区间完整位于一个有效开放窗口。
- 不与有效排单的占用区间、临时封档相交。

采用左闭右开区间 [开始, 结束)，相交条件为 A.start < B.end 且 B.start < A.end。前一占用在 11:30 结束，后一占用可从 11:30 开始。非整点排单也按真实分钟计算。

示例：开放 09:00–12:00、13:00–18:00；拍摄 90 分钟；前置 0、后置 30 分钟。客户约 09:30–11:00，实际占用 09:30–11:30，下一单最早 11:30，但 90 分钟加缓冲无法容纳在上午窗口内，因此下一次可约开始为 13:00。不能因 11:30 空闲就展示为该时长可约。

日期可约状态必须按所选时长计算，不能只看当天有无空闲。

## 7. 统一状态与收款规则

| 状态 | 建议占用规则 |
| --- | --- |
| normal 正常排单 | 占用 |
| completed 已完成 | 保留原占用，禁止借由提前完单把尚未过去的时间再次放出 |
| stored 暂存 | 不占用；恢复时重新校验 |
| pending_confirm 现存兼容状态 | 明确其历史含义前，保守视为占用；首期不新增审批流程 |
| displayStatus=N 删除记录 | 不占用 |
| 临时封档 | 占用 |

未付定金的有效预约仍占用，不因为未收款自动释放。后续如引入支付超时，需要单独定义明确的预约状态和释放机制。

公众提交、手工新增、编辑、恢复、完单等动作均使用同一占用口径。编辑或恢复时排除自身，并在修改占用前重新校验。正常转暂存或删除后释放；恢复重新检查；改期必须原子释放旧区间并占用新区间。

## 8. 接口与数据建议

复用 /api/public/availability，增加服务时长参数，返回可约开始时间及对应结束时间；日期摘要提供按时长计算的日历可约状态。公开接口只返回必要时间信息，不返回客户姓名、电话、订单详情或私人封档原因。

公众提交以 providerId、serviceTypeCode/角色、durationMinutes、startTime 为核心；结束时间和占用区间由服务端计算。过渡期如果仍传 endTime，后端必须校验与计算值一致。旧客户端也必须遵守时长上限，不留旧字段绕过入口。

建议新增：

- 服务者预约规则：开放开关、周窗口、预约范围、缓冲默认值。
- 服务者服务选项：服务类型、允许时长和默认时长。
- 特殊日期规则：覆盖窗口或关闭全天。
- 临时封档：服务者、日期、起止、原因、有效状态。
- 排单预约规则快照：本次时长、前后缓冲、规则版本、来源及必要的覆盖理由。
- 服务者日期锁记录：唯一键 (provider_id, date)，用于并发串行校验。

已有 startTime/endTime 保持表示实际服务时间，缓冲另外保存，避免客户把缓冲当成付费拍摄时间。具体实体和 API 名称在实施时确定。

## 9. 并发与完整登记

可约查询是展示快照，最终提交必须重新校验。

- 在数据库事务内创建或取得服务者日期锁记录，并加行锁；不能仅锁现有排单，因为空白日期没有排单可锁。
- 获取锁后重新读取当前规则、有效排单和封档，计算并验证占用，然后完成写入。
- 公共提交、管理端新增/编辑/恢复、封档写入均走相同锁协议；释放占用和状态切换也纳入协议。
- 改期锁旧日期和新日期，多服务者一次提交按稳定的服务者/日期排序取锁，避免死锁。
- 多服务者预约的组、客户、全部排单在同一个事务中完成，一项失败整单回滚。
- 公共提交增加幂等请求标识，同一请求重试返回原结果，不重复生成订单。
- 时间已被占用返回 409 及通用提示，前端刷新档期并保留其他表单内容。
- 规则变更明确生效时点；提交在事务内使用已读取并验证的版本，若发生版本变化则重新校验，避免查询到旧规则却按旧规则登记。

不以进程内变量锁或前端禁用按钮替代数据库并发保证，不在浏览或选择开始时间时创建长期占位。

## 10. 历史数据与上线

- 不自动缩短、删除或重新计算已有客户服务时长。
- 历史有效长单仍占用原区间，列出异常长单供服务者人工核对和改期。
- 历史单缺少缓冲快照时按 0 缓冲兼容；新规则用于新预约。为已有单补缓冲应由服务者明确处理，先检查冲突。
- 周规则和公众开放时长由服务者确认；未配置的账号展示「暂未开放线上档期」，仍可手工登记。上线前提供推荐模板和预览，不默认为全天开放。
- 改营业时间不追溯取消已有预约；已有单继续占用，后续新预约遵循新窗口。
- 统一规则前核查 pending_confirm 的实际使用及未来 completed 记录，不擅自批量改变状态。
- 先修复公众任意时长与查询口径，再发布统一档期管理；前后端合同协调上线，部署前审查新增表和字段影响。

## 11. 实施阶段

### 第一阶段：立即解决过长预约

移除整段空闲一键填入；公众改为允许时长 + 开始时间；服务端约束时长、推导结束；统一资源和状态口径；修复 24:00、非整点、加载失败；提交加资源锁和整单事务。

阶段一采用明确的临时营业规则并让服务者确认，不能仅限制时长却继续默认允许凌晨预约。

### 第二阶段：服务者自主档期管理

落地周窗口、特殊日期、封档、前后缓冲、提前量、预约范围和日历展示；打通手工登记、编辑与恢复。

### 第三阶段：按实际业务扩展

可选半天/全天服务、不同拍摄类型时长、外景交通缓冲、改期操作记录。跨日业务、多资源或多人容量另行设计；不提前加入复杂排班系统。

## 12. 验收重点

- 空白全天选择 90 分钟，只生成 90 分钟服务及配置缓冲，不占满全天。
- 客户不能通过改请求体提交未开放的长时段或越过营业时间。
- 90 分钟放不下的空隙不展示为可选开始。
- 午休、休假、封档、提前量和最远日期均正确生效。
- 09:10–10:10 的历史单正确阻挡相交候选。
- 同一人的不同角色共享占用，不同服务者互不影响。
- 暂存/删除释放，恢复重新校验，完成状态不意外放出未来区间。
- 查询后被别人占用时提交明确失败，保留表单并刷新档期。
- 两个并发请求抢同一占用，最多一个成功。
- 多服务者任一冲突整单回滚，幂等重试不重复登记。
- 编辑改期、封档与公众提交并发时没有重叠或部分更新。
- 营业规则变化不改写历史预约；旧客户端不能绕过新限制。
- 普通入口和专属二维码入口使用同一规则，移动端加载/空/错误状态正确。

本轮仅进行了静态代码检查，未运行预约联调或自动化测试；这些验收项为实施后的验证要求。
